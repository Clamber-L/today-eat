# 核心功能：库存驱动的菜谱与每日清单

版本：v0.1　日期：2026-10-06　配套文档：`docs/PRD.md`、`docs/RECIPE.md`、`docs/UI.md`

本文描述产品的主功能：用户家里有什么，就推荐或生成能做的菜，排进每天的清单，做完扣库存，再影响后面的安排。

## 1. 核心闭环

```
        ┌──────────── 购物入库 ◀──── 购物清单 ◀───┐
        ▼                                        │
   我的食材库 ──▶ 可做的菜（匹配 + AI 生成）──▶ 一周清单
        ▲                                        │
        │                                        ▼
        └──── 打卡扣库存 ◀──── 烹饪模式 ◀──── 今天这一餐
```

三个关键结合点：
1. 清单生成时，优先使用库存里的食材，尤其是临期食材
2. 菜谱库里凑不出合适的菜时，用库存食材由 AI 生成新菜补位
3. 做完一餐打卡，扣减库存，后面几天的清单会检查食材够不够

## 2. 管理员知识库（AI 的资料基础）

AI 生成和解析菜谱的质量，取决于后台的资料。生成时后端会从知识库里检索相关条目，作为上下文交给模型；模型的输出也必须落在知识库的取值范围内。所以知识库是管理员最主要的工作。

| 资料 | 内容 | 作用 | 优先级 |
|---|---|---|---|
| 食材百科 | 分类、别名、单位换算、保质期、存放方式、应季月份、可替代食材、常见处理方式 | 食材匹配、购物清单、替换 | P0 |
| 调料百科 | 风味（咸、鲜、甜、酸、辣、香）、盐糖折算系数、可替代调料、常用量范围 | 生成配料、油盐糖计算 | P0 |
| 烹饪参数表 | 食材 × 做法 × 口感 → 火力、时长、判断标准，例如"西兰花 × 焯水 × 脆 → 大火，水开后 1 分钟，颜色变翠绿" | 生成步骤的时长和判断标准，口感分支 | P0 |
| 动作预设、切法、术语表 | 见 RECIPE.md 第 5、6 节 | 步骤结构 | P0 |
| 风味模板 | 常见味型的调料配比，以 2 人份为基准：鱼香、糖醋、宫保、葱油、蒜蓉、红烧、清蒸、凉拌、番茄、咖喱等 | 生成料汁和腌料 | P0 |
| 搭配规则 | 食材之间的常见搭配（番茄 + 鸡蛋、青椒 + 肉丝）以及不推荐的组合 | 生成时组合食材 | P1 |
| 健康改良规则 | 减油减糖的替换方法：油炸 → 空气炸锅，糖醋 → 减糖版配比，五花肉 → 里脊 | 健康改良 | P1 |
| 官方菜谱库 | 结构化、经过审核的菜谱 | 匹配候选、AI 生成时的参考范例 | P0 |

录入方式：
- 食材百科、调料百科、风味模板：先由 AI 批量生成草稿，管理员逐条审核，审核状态记录在条目上
- 烹饪参数表：先从官方菜谱中自动抽取（每道菜的每一步都是一条"食材 × 做法 × 时长"样本），再由管理员整理合并
- 每条资料都有"已审核 / 未审核"状态，AI 生成时只使用已审核的条目

## 3. 可做的菜：库存匹配

### 3.1 可做度

对每道菜计算它和用户库存的匹配情况：

| 指标 | 计算 |
|---|---|
| 主料覆盖率 | 库存中有的主料 ÷ 主料总数（按用量判断，不只看有没有） |
| 辅料覆盖率 | 同上，辅料葱姜蒜计入，但权重低 |
| 调料齐全 | 常备调料是否都标记为"有" |
| 缺少的食材 | 缺什么、缺多少 |
| 临期命中 | 用到了几种 3 天内过期的食材 |

可做度分级：

| 等级 | 条件 | 界面 |
|---|---|---|
| 现在就能做 | 主料、辅料、调料都够 | 绿色"能做" |
| 差一点 | 缺 1～2 种辅料或调料，或有可替代的食材 | 黄色"缺 2 样"，显示缺什么、能用什么代替 |
| 需要买 | 缺主料 | 不标记，按普通菜谱显示 |

替代：当缺少的食材在食材百科里有可替代项，并且库存里正好有替代品时，视为"差一点"，显示"用香菇代替口蘑"。

### 3.2 入口

- 菜谱页新增"能做"筛选，按可做度和临期命中排序
- 食材页的临期食材可以点"用它做菜"，筛出用到这种食材的菜谱
- 首页"今天"的菜如果因为库存变化做不了了，会提示并给出替换建议

## 4. AI 生成新菜（基于我的食材）

当菜谱库里没有合适的菜，或者用户主动想"用家里的东西做点新的"时使用。

### 4.1 触发方式

| 触发 | 说明 |
|---|---|
| 用户主动 | 菜谱页"✨ 用家里的食材做菜"：可以选几种想用的食材、角色（荤菜、素菜…）、口味、时长上限 |
| 清单补位 | 生成清单时某个槽位没有候选，或候选的最高分低于阈值，由 AI 生成补位，见 5.3 |
| 临期消耗 | 食材页"用它做菜"在菜谱库里找不到结果时，提供"让 AI 想一道" |

### 4.2 生成约束

输入给模型的信息：
- 可用食材：用户库存（含数量）+ 常备调料
- 指定的食材（如果用户选了）和角色
- 健康约束：由当前健康规则推出，比如本周高油高糖已满额时，只允许蒸、煮、快炒、凉拌
- 忌口与过敏
- 从知识库检索出的相关条目：涉及食材的百科、烹饪参数、适用的风味模板、2～3 道相似的官方菜谱作为范例

硬约束（由后端校验，不只依赖模型自觉）：
- 主料只能来自库存；辅料和调料最多允许缺 1 种，缺的那种标记为"需购买"
- 所有食材必须能匹配到食材字典
- 用量不能超过库存数量
- 结构必须符合 RECIPE.md，通过 9.3 的校验规则（按官方标准校验）
- 火力和时长要落在烹饪参数表的范围内；超出范围的字段标记为"待确认"
- 健康分不低于用户设置的下限

校验失败时，带着错误信息让模型重试一次；还是失败就返回失败原因，不给用户看一份不合格的菜谱。

### 4.3 生成结果

- 一次给 3 个方案，每个方案显示菜名、主要食材、时长、健康分、"用掉了哪些临期食材"
- 用户选一个，进入确认页，保存为"我的菜谱"，来源标记为 `ai_generated`
- 不选也可以，"换一批"重新生成
- 做完后提示用户打分。评分高的 AI 菜会更常出现在清单里；管理员后台可以看到被高频收藏的 AI 菜，审核后收录为官方菜谱

## 5. 与一周清单结合

### 5.1 生成偏好

生成设置弹层新增一个选项：

| 选项 | 说明 |
|---|---|
| 优先用家里的（默认） | 可做度和临期命中的权重高，尽量减少购物 |
| 均衡 | 健康和多样性优先，库存只是加分项 |
| 不考虑库存 | 只按健康和口味选，之后统一买 |

### 5.2 打分调整

在 PRD 8.2 的打分基础上增加：

```
+ 可做度分（现在就能做 > 差一点 > 需要买）× 偏好权重
+ 临期命中分（越快过期，分越高）
+ 食材复用分：本周已经要买的食材，再次用到时加分（一把芹菜分两天用完）
− 购买成本：需要额外购买的主料种类越多，扣分越多
```

库存的分配要按时间顺序扣减：周一的菜用掉 2 个鸡蛋之后，周二再计算可做度时，用的是扣掉之后的库存（模拟库存）。

### 5.3 AI 补位

```
规则算法先完整跑一遍
  ↓
找出"空缺"或"最高分低于阈值"的槽位
  ↓
对这些槽位异步调用 AI 生成（用模拟库存中剩下的食材）
  ↓
生成结果以"✨ 新菜"标记出现在预览里，用户可以接受、换一道或替换成库存菜谱
```

- 规则算法负责整体结构和健康规则，AI 只填空，保证结果可控
- 每次生成最多补 3 个槽位，控制成本和等待时间
- 用户可以在设置里关掉 AI 补位

### 5.4 一餐统筹（多道菜同时做）

两菜一汤或家庭聚会时，难点是几道菜怎么安排顺序，才能差不多同时出锅。系统把这一餐所有菜谱的准备和烹饪步骤合并成一条时间线：

- 先排耗时长、可以等待的：炖汤、焖饭、腌制、泡发
- 准备阶段合并：所有菜的葱姜蒜一起切，备料碗按菜分组，颜色区分
- 炒菜放在最后，按"凉了影响大"的顺序倒排，最后出锅的是最需要趁热吃的菜
- 默认单灶，也可以设置成双灶；蒸锅、电饭煲、烤箱这类不占灶的厨具可以并行

```
17:30  开始
17:30  ▶ 冬瓜排骨汤：焯排骨 → 下锅炖（等 40 分钟）
17:40  ▶ 准备：切青椒丝、肉丝、腌肉、调料汁；洗西兰花
17:55  ▶ 杂粮饭：电饭煲开始煮
18:05  ▶ 炒：蒜蓉西兰花
18:10  ▶ 炒：青椒肉丝
18:15  ▶ 汤加冬瓜，5 分钟后出锅
18:20  开饭
```

用户在首页的这一餐上点"开始做饭"，进入统筹版的烹饪模式：顶部同时显示多个倒计时（汤 32:10、饭 18:40），每一步标明是哪道菜。

用户在设置里填"一般几点开饭"，系统由此倒推开始时间，并提前推送"17:30 该开始做饭了"。

时间线由后端算法根据步骤的时长、是否可等待、厨具占用来排，不需要 AI。

### 5.5 提前提醒

根据清单和库存，在前一天自动生成提醒：
- 解冻："明天晚饭要用冷冻的鸡胸肉，今晚放到冷藏室解冻"
- 泡发："明天的木耳炒蛋需要提前 2 小时泡发木耳"
- 提前腌制：等待时长超过 2 小时的腌制
- 缺货："周四的清蒸鲈鱼还没买鲈鱼"

提醒时间可以设置，默认前一天 21:00。

### 5.6 打卡与库存回写

- 烹饪模式结束，或者在首页点"吃过了"，就算完成打卡，按实际份数扣减库存
- 没做的那一餐可以标记"没做 / 吃外卖"，食材不扣减；系统检查这些食材会不会过期，必要时提示把这道菜挪到明天
- 扣减后重新计算后面几天的可做度。如果某天的菜做不了，在首页提示，给出"替换"或"加入购物清单"两个选项
- 库存数量允许手动校正。实际库存和系统记录总会有偏差，所以界面上提供"快速盘点"：按存放位置逐项确认还有没有

## 6. 菜谱导入来源

### 6.1 导入流程

```
获取原始内容 → 提取文字（HTML 解析 / OCR / 语音转文字）→ AI 结构化（结合知识库）
→ 匹配食材字典 → 校验 + 补全 → 查重 → 草稿 → 用户确认
```

查重：和用户已有菜谱、官方菜谱比较菜名和主料。相似度高时提示"你已经有《番茄炒蛋》了，要合并还是另存？"

### 6.2 各来源的处理方式

| 来源 | 用户操作 | 系统处理 | 说明 |
|---|---|---|---|
| 抖音、小红书 | 在 App 里点"分享"→ 选择本 App；或者复制分享文本粘贴进来；也可以上传截图 | 解析分享文本中的标题和描述；截图用多模态模型识别；链接只保存为来源 | 不抓取平台页面，不下载视频（见 6.3） |
| 自己保存的视频 | 从相册选择视频 | 抽取关键帧 + 语音转文字 → 结构化；关键帧可以作为步骤的参考图，用户确认后再保存 | 视频处理成本较高，P1 |
| GitHub | 粘贴仓库里菜谱文件的链接 | 拉取 Markdown 原文 → 结构化 | 先检查仓库的开源协议 |
| 普通网页（下厨房等） | 粘贴链接 | 抓取页面正文 → 结构化 | 只供用户个人使用 |
| 纯文字 | 粘贴 | 直接结构化 | 比如朋友发来的做法 |
| 菜名 | 输入 | 基于知识库直接生成 | |

系统分享菜单接收（iOS Share Extension、Android Intent Filter）是体验最好的入口：用户在抖音、小红书看到菜谱，点分享就能直接导入，不用切换应用。这一项建议放进 P0。

### 6.3 版权与平台规则

- 抖音、小红书的服务条款通常禁止未经授权的抓取，也没有开放内容接口，所以不做服务端抓取。只处理用户主动提供的分享文本、截图和自己保存的视频
- 导入的菜谱默认是"仅自己可见"，只保存提取出的结构化信息（用料、步骤），不保存原文全文、原图和原视频；详情页显示来源平台、作者名和原链接，可以跳回原内容
- 来源是第三方的菜谱，不能开启公开分享或投稿，除非用户声明是自己的原创内容
- GitHub 上的 HowToCook（程序员做饭指南）使用 Unlicense 协议，属于公有领域，适合管理员批量导入作为官方种子菜谱。它的菜谱用 Markdown 写成，用量精确、结构统一，转换难度低。导入前需要再确认一次仓库里的 LICENSE 文件
- 其他 GitHub 仓库按各自的协议处理：没有协议的视为保留所有权利，只供个人导入

### 6.4 官方批量导入（管理员）

```
选择来源（HowToCook 仓库 / 一批菜名 / 一批网页）
→ 批量任务，逐条 AI 结构化
→ 进入审核列表：按完整度、校验结果排序
→ 管理员逐条审核、补结果图，然后发布
```

HowToCook 导入的同时可以顺便积累知识库：从步骤里抽取"食材 × 做法 × 时长"写入烹饪参数表（未审核状态），从 tips 目录整理术语表。

## 11. 风险

| 风险 | 应对 |
|---|---|
| AI 生成的步骤不安全或做不出来 | 知识库约束 + 后端硬校验 + 烹饪参数范围检查；AI 菜显示"✨ AI 生成，首次制作请留意判断标准" |
| 库存数据不准，导致"能做"判断错误 | 快速盘点；"差一点"等级留出容错；打卡时允许修改实际用量 |
| 知识库录入工作量大 | AI 起草 + 人工审核；从 HowToCook 和官方菜谱自动抽取；先覆盖最常用的 150 种食材 |
| AI 调用成本 | 规则算法为主，AI 只补位；结果缓存；每日配额 |
| 第三方平台内容的版权 | 不抓取、不存原文原图、保留来源，默认仅自己可见 |
