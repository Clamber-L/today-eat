## 2. 导入流水线

```
① 解析（规则）→ ② 结构化（AI）→ ③ 食材匹配 → ④ 校验 + 健康标注 → ⑤ 审核 → ⑥ 发布
```

每一步的产出都落地为中间 JSON 文件，方便重跑某一步、对比差异：

```
seed/
  raw/{category}/{slug}.json         ① 解析结果
  structured/{category}/{slug}.json  ② AI 结构化结果
  matched/…                          ③ 食材匹配后
  report/{slug}.json                 ④ 校验报告、健康分
  knowledge/                         知识库草稿：ingredients、glossary、cooking_params、flavors
  manifest.json                      上游 commit、每篇文件的 hash 与处理状态
```

### ① 规则解析（不调用 AI）

按 Markdown 章节拆出：

| 字段 | 来源 |
|---|---|
| name | 一级标题，去掉"的做法" |
| summary | 标题后第一段 |
| cover | 第一张图片（相对路径） |
| difficulty_stars | "预估烹饪难度"的星数 |
| calories_ref | "预估卡路里"，只作参考 |
| equipment_hint | "必备原料和工具"中的厨具词（空气炸锅、微波炉、电饭煲、烤箱、高压锅） |
| ingredients_raw | "计算"章节的列表，保留分组标题（必须配料 / 进阶配料 / 可选配料） |
| servings_raw | "计算"中"一份够 N 人"的描述 |
| versions | "操作"下的三级标题；没有三级标题则只有一个版本 |
| steps_raw | 每个版本的编号列表，保留缩进的子项（子项通常是可选做法或注意事项） |
| extras_raw | "附加内容"，去掉固定的结尾句 |
| source_path、source_hash | 文件路径与内容 hash |

用料行用正则预解析：`名称 = 数值 单位`、`名称 数值单位`、区间、`* 份数` 公式、括号注释（约 180g）。解析不了的保留原文，交给 ②。

### ② AI 结构化

输入：① 的结果 + RECIPE.md 的 JSON Schema + 知识库中的动作预设、切法、相关烹饪参数。输出：符合 RECIPE.md 第 10 节的菜谱 JSON。

要做的事情：
1. 拆出准备阶段：把切配、泡发、腌制、调汁从步骤列表里提出来，组成备料碗；原文中 `` `西红柿块` `` 这类命名直接作为碗名
2. 拆分烹饪步骤：一步一个动作，原文"转大火，下入花生和辣椒，加鸡精、醋、糖，翻炒均匀"拆成 2～3 步
3. 补全每步的火力、时长区间、判断标准；原文写了的必须沿用，补全的写入 `ai_fields`
4. 原文的子项：可选做法写进贴士，注意事项写进"注意"
5. 用料归位：每种用料挂到它第一次出现的备料碗或步骤上，保证"用量只填一次"
6. 份数统一为 2 人份：公式按份数 = 2 计算；区间保留为区间，取中间值作为默认值
7. 识别口感分支：原文出现"至自己想要的浓度""喜欢软一点可以多煮"等描述时生成分支
8. 标注角色、餐次、烹饪方式、蛋白质来源、蔬菜占比、菜系

约束：
- 不允许引入原文没有的食材（与 HowToCook 自己的规则一致），清水除外
- 原文给出的数值不得修改，只能补充
- 输出必须通过 JSON Schema 校验，不通过就带错误重试一次，仍失败则标记为"需人工处理"

### ③ 食材匹配

- 把用料名称对应到食材字典：先精确匹配，再查别名（西红柿 → 番茄、手枪腿 → 鸡腿），再让 AI 判断
- 括号里的替代写法（"手枪腿（或者鸡胸脯肉）"）拆成主料 + 替代品，替代品写进食材百科
- 品牌建议（"推荐品牌好侍"）写进用料备注
- 字典里没有的食材，汇总成待新建列表，交给管理员和知识库流程（见第 3 节）
- 不同单位换算到食材的基础单位；缺少换算系数的（"大葱 1 根"）用原文括号里的重量，没有就记入待补系数列表

### ④ 校验与健康标注

- 按 RECIPE.md 9.3 的官方标准校验，生成报告：错误、警告、完整度
- 按 PRD 6.4 计算每人份的油盐糖等级和健康分
- 自动打标：
  - 高油高糖菜（油炸、多油、多糖）：保留导入，但会被健康规则限制出现频次
  - 健康改良候选：健康分 < 0 的菜，进入 P1 的健康改良队列，生成减油减糖版本

### ⑤ 审核（管理员后台）

审核列表按"错误数 → 完整度 → 健康分"排序。每道菜的审核页左边显示原 Markdown，右边显示结构化结果，AI 补全的字段高亮。

审核要点：
- 备料碗拆分是否合理，有没有漏掉的用料
- AI 补全的火力、时长、判断标准是否可信（重点看肉类和海鲜是否熟透）
- 角色和健康属性是否正确
- 封面图是否可用

### ⑥ 发布

- 图片上传到对象存储，替换为 media_id
- 写入 `owner_type = system`、`origin = official_import`、`source_platform = github`、`source_url` 指向 GitHub 上的原文件
- 首次发布生成 RecipeRevision v1

## 3. 知识库的同步提取

| 来源 | 提取内容 | 去向 |
|---|---|---|
| 全部菜谱的用料 | 食材名称、别名、常见用量、单位与重量换算（"1 个约 180g"） | 食材百科、IngredientUnit |
| 全部菜谱的步骤 | 食材 × 动作 × 时长 × 火力 × 判断标准 | 烹饪参数表（未审核），按食材和动作聚合，取中位数和区间 |
| tips/learn/*.md | 焯水、炒、煎、凉拌、腌、蒸、煮的方法与判断标准 | 动作预设的默认值、术语表 |
| tips/advanced/油温判断技巧.md | 油温分级和判断方法 | 油温参考表（RECIPE.md 5.2） |
| tips/advanced/高级专业术语.md | 术语解释 | 术语表 |
| tips/learn/食品安全.md、去腥.md | 安全提醒、去腥方法 | 动作预设的"注意"、贴士库 |
| dishes/condiment | 葱油、糖醋汁、蒜香酱油、油泼辣子等 | 风味模板，或者作为可被其他菜引用的"自制调料" |

调料百科里的盐糖折算系数（生抽、蚝油、老抽等）由管理员按常见产品的营养成分表填写，不从仓库里提取。

## 4. 特殊情况

### 4.1 难度换算

| HowToCook | today-eat |
|---|---|
| ★ ～ ★★ | 1 简单 |
| ★★★ | 2 普通 |
| ★★★★ ～ ★★★★★ | 3 较难 |

### 4.2 角色判定

先按目录给出默认角色，再由 AI 根据主料修正：
- vegetable_dish 里有肉或蛋的 → 荤素搭配
- meat_dish 里蔬菜用量占一半以上的 → 荤素搭配
- breakfast 按主要成分拆为早餐主食（燕麦、三明治、花卷）和早餐蛋白（各种蛋）

### 4.3 一碗饭类主食

staple 里约一半是"完整的一餐"：盖饭、炒饭、拌面、汤面、炒河粉。新增一个餐型模板"一碗饭"（这一道 + 可选的一个素菜或汤），这类菜的角色记为 `one_bowl`。纯主食（米饭、馒头、烙饼）仍然是 `staple`。

需要同步修改 PRD 5.1 的角色表和 5.2 的模板表。

### 4.4 多版本菜谱

83 篇有多个版本。处理方式：
- 第一个版本（通常是简易版）作为主菜谱
- 其他版本导入为独立菜谱，名称加后缀（"宫保鸡丁（进阶版）"），`source_recipe_id` 指向主菜谱，默认不参与清单生成，用户可以手动开启
- 版本之间只是"可选配料"不同的，合并为一个菜谱，差异部分作为可选用料

### 4.5 不适合清单的菜

需要专门设备、耗时超过 3 小时、或者明显是节日菜的，导入后打上"周末菜 / 特殊场合"标签，不参与工作日生成。

## 5. 上游同步

- `manifest.json` 记录导入时的上游 commit 和每个文件的 hash
- 以后定期 `git pull`，用 `git diff --name-status <旧 commit> <新 commit> -- dishes/` 找出新增、修改、删除的文件
- 新增文件走完整流水线；修改的文件重新解析后生成新的 RecipeRevision 草稿，由管理员确认后发布；上游删除的文件只提示，不自动下线
- 已被管理员手动修改过的字段，同步时不覆盖，只在审核页里提示上游有变化

## 6. 分批计划

| 批次 | 内容 | 数量 | 目标 |
|---|---|---|---|
| 第 1 批 | 简单、家常、健康分较高的菜：各角色挑选，覆盖一周不重复 | 约 80 | 验证流水线，让清单生成先跑起来 |
| 第 2 批 | 剩余的荤菜、素菜、水产、汤 | 约 150 | 丰富候选 |
| 第 3 批 | 主食、早餐、多版本、特殊菜 | 约 80 | 补齐 |

第 1 批的建议筛选条件：难度 ≤ ★★★，无油炸，原文步骤 ≤ 12 步，不需要特殊设备。

## 7. 实现建议

- 流水线写成独立的命令行工具，和后端分开部署；可以用 Rust 写，以便复用后端的菜谱模型和校验逻辑，也可以用 Python 快速迭代，最后把产出的 JSON 通过后台的批量导入接口写入
- 规则解析（①）和校验（④）都是确定性的，要写单元测试，用仓库里的真实文件做测试样例
- AI 结构化（②）记录每次调用的 prompt 版本和模型版本，方便以后整体重跑
- 成本：每道菜一次结构化调用，必要时加一次重试，311 道菜整体成本可控；建议先用 10 道菜调好 prompt，再跑第 1 批
